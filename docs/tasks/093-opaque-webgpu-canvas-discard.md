## Required observations

The original canvas uses alpha false, clears red and is copied in the drawing task. It is copied again after the upstream helper counts five animation frames. The discard assertions require the first copy to be red and the second opaque black. Its visual reference also keeps the source square red. The preserve case expects all three red. The pinned WebGL drawing-buffer section specifies clearing the default attachments after presentation and only publishing after a creation, resize or draw. It also cautions that consuming the discard buffer as an image after the rendering function returns may give undefined results. The conformance target here is the exact original assertion and the browser control. [Pinned original](https://github.com/KhronosGroup/WebGL/blob/39443210f7f81db4773eb104facadfb85d05dfa4/sdk/tests/conformance/context/context-attribute-preserve-drawing-buffer.html) · [Pinned WebGL drawing-buffer rules](https://github.com/KhronosGroup/WebGL/blob/39443210f7f81db4773eb104facadfb85d05dfa4/specs/latest/1.0/index.html#THE_DRAWING_BUFFER)

WebGPU's HTML snapshot algorithm applies opaque alpha to an external read such as drawImage. Rendering expires the current texture and records the presented image, while acquiring a new texture can replace the drawing buffer. Expiry itself leaves the drawing-buffer storage intact. Thus a browser fix to return opaque alpha on snapshots may change RGB retention as well. Re-run #48 after such a change. Chrome 158 source dispatches direct HTML canvas copies to a back-buffer snapshot, placeholder reads to an exported frame, and 2D/bitmaprenderer reads to their current image. Its WebGPU backend clears its current texture reference on canvas transfer. A later getCurrentTexture marks a new mailbox texture for presentation even when the application never encodes a draw. The probe observes the resulting read and display separately. The exact internal branch generating alpha zero was not traced. [WebGPU canvas snapshot and HTML hooks](https://www.w3.org/TR/2026/CRD-webgpu-20261116/#canvas-context) · [Chrome 158 HTMLCanvasElement](https://github.com/chromium/chromium/blob/158.0.8127.36/third_party/blink/renderer/core/html/canvas/html_canvas_element.cc#L1969) · [Chrome 158 GPUCanvasContext](https://github.com/chromium/chromium/blob/158.0.8127.36/third_party/blink/renderer/modules/webgpu/gpu_canvas_context.cc#L272)

## Chrome results

Chrome 158.0.8127.36 on Apple Metal 3 completed the official file at main 6eb6c87. Native passed 4/4, JS and Rust each passed three and failed the discard assertion. Their preserve branch passed. The CSS backdrop in the independent probe is green so that an empty composited layer, black and red are distinguishable in the screenshots. Its source canvas remains mounted. A new default-alpha 2D destination copies the source pixel at each sampling point.

The last route uploads the private GPU canvas via native texImage2D, attaches the texture to a read framebuffer and uses blitFramebuffer to the native default framebuffer. This probe makes no JavaScript pixel download. Adding this route to production would require a native GL presentation context per affected visible canvas, native-resource limits/lifecycle handling, and a cross-API image upload and blit per published frame. Its latency and memory cost have not been measured. [ADR 008](../adr/008-dom-image-extraction.md) permits a private native WebGL context for extraction of image pixels. Making a visible HTML canvas depend on native GL to present plain draw calls requires a separate product decision.
