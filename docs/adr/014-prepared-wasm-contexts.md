# ADR 014 — Isolated Rust contexts in one prepared WebAssembly instance

A prepared factory owns one GPU device. Its Rust backend lazily instantiates the semantic module when the first context is acquired. Every logical WebGL context still owns its BufferCore, rendering state, input arena, replies, and pending commands. Different prepared factories and different worker realms own independent instances. Direct single-context consumers of ABI6 can continue to use the original exports.

Two optional exports park and select the complete current state or release a parked state. The adapter assigns monotonically increasing private selectors per factory and checks the selected context before each actual Wasm call. Compiler or host callbacks can enter another context and throw. Subsequent Wasm calls, including an automatic flush, select their originating state again. Selection does not change logical handles, context ownership or GL-visible identities. The adapter still copies owned reply payloads before invoking external code. Explicit disposal releases GL objects and transport storage and preserves the original lost-state behavior on retained references. Garbage collection releases the vacant context namespace when its adapter is unreachable.

WebAssembly.Module compilation was already shared, but creating a distinct Instance and linear memory for each Window context exhausted Chrome's Wasm reservations in the 96-context original bitmap-transfer workload. Discarding strong test-harness references reclaimed sixteen Window facades yet still exhausted the old strategy after 92 contexts. This decision targets that observed resource limit. No shared memory, cross-origin isolation or external runtime dependency is required.
